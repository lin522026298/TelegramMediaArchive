# 0.1.9 调度、失败冷却和运行证据

## 改动与约束

- 按原日期/消息号/媒体序号顺序启动有界 worker 池。完成或普通失败立即补位，保留文件路径、独立 part、实际长度续传和完整长度检查/原子发布。空间预检继续预留 20 GiB，并保守计入活跃任务和下一任务的完整大小。
- 下载/索引无进展时先取消并等待全部活跃请求和迭代器，再断开唯一客户端。重连只继续尚未分派的本轮队列；已失败/被取消的文件保留下一轮处理，不从最老坏文件重新开始。
- 兼容新增 `media_retry` 表，不改原媒体主键、路径或归档状态。首次导入旧错误的重试次数但不伪造原始响应；重开不会重置冷却。普通错误 300 秒起指数退避，上限 21600 秒；空消息/无媒体 86400 秒；权限错误 3600 秒。成功清理当前冷却条目，原媒体重试计数仍保留。
- `get_messages`/图片准备阶段异常也进入分类，避免漏记；请求客户端保留最后一次 RPC 错误类型，不再只输出掩盖根因的请求次数。
- `diagnose-unavailable` 在原会话 OS 锁内逐批取原始消息响应，区分 MessageEmpty、消息存在但无媒体、当前可见媒体；保存不含凭据的类型观察。空返回不等于可证实删除。可见媒体转回 pending 时不重置路径或断点。
- GUI 下载页的“重试冷却中的错误项”和“复查不可用媒体”均走已有命令互斥。前者只释放一次已有冷却，不让 watch 永久忽略退避；后者只复查，完成后可继续未完成下载。
- 独立 JSONL 日志按 GUI/CLI/上传器记录 run id、时间、PID/父 PID、Job 归属、正常退出/异常类型和节流进度，不写密钥、群名或媒体文件名。日志各 2 MiB，3 份轮换。强杀、断电等无法运行 finally 的情况只记为缺少退出证据，不编造根因。
- 手动工具脚本先检查自身 Job 归属。需要时用 Win32_Process.Create + ShowWindow=0 创建一次性独立 PowerShell 主机，核实新主机不在 Job 内后再启动原业务。禁止递归重试或静默降级到未隔离主机；不配置系统自启动。

## 验证与部署

自动化回归包含慢任务不阻塞补位、有界并发和顺序、磁盘门限、未分派游标、取消收尾、持久冷却、旧库幂等迁移、权限错误不误判缺失、原始响应三类、双语 UI 命令、独立运行证据等。旧图片/视频与云删除安全测试继续执行。真实部署证据只保存在本机，不将账号、群号、媒体名、会话和数据库放入公开提交。

Windows 回归 104 项全部通过（包含隔离本地 rclone crypt 全流恢复校验，无跳过）；Tk 测试在构造后立即隐藏。独立主机合成探针实测 Job 归属为 false，前后台窗口句柄未变化。这不代替真实 Telegram/网盘部署验收。

本修复不能保证 Telegram 上游所有历史文件恢复，也不能反向证明此前某日中断的具体原因。没有自启动时，电脑关机或全部业务被外部结束仍需用户手动启动。
