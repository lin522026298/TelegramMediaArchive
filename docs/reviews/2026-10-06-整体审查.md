# 2026-10-06 整体审查

更新：本文件保留原审查证据。R1–R10 已在 0.1.7 中修复，当前行为与验收见
[0.1.7-修复验收.md](0.1.7-修复验收.md)。以下“未修复/待修”均描述审查当时的基线，不是当前版本状态。

范围：下载/索引/续传、SQLite、GUI 生命周期与设置、加密上传和删除、启动停止、
恢复脚本、源码与发布包。基线为当前 0.1.6 工作区，不控制用户鼠标键盘。

## 结论

这套实现可以继续作为当前单群、单实例任务的内核，但尚不适合以“任意用户操作均安全”
的成品标准发布。下面的问题不是对旧模型能力的评价，而是明确的工程行为和测试缺口。
原停滞修复已部署；以下新发现项仅审查，尚未修复或重构。

当前现场只有一个群组的数据、一个实际 CLI 会话所有者，上传队列没有延迟待清理项，
所以最高风险场景尚未触发。不能据此推导未来不会触发，也没有发现当前文件已经损坏的证据。

## 待修问题

### R1 / P1：切换群组会让旧群待下载项通过新群连接处理

位置：`tg_media_archive.py:324`、`:941`、`:805`；路径生成 `:144`。
数据库键包含 chat_id，但 list_pending 不按当前 chat_id 过滤；所有记录交给同一个
已选 entity 的 get_messages。一个目录先索引 A，再切换索引 B，A 的消息号会从 B
读取，可能下错内容或报缺失。文件路径也不含 chat_id，同时间、消息号、文件名的
两个群记录会碰撞。临时库已复现混群查询和路径碰撞。

建议：先明确一根目录一群的持久绑定并拒绝误切；若支持多群，所有查询、路径、
session/entity 分发、云远端键都要按群隔离，不能只加一个 SQL 条件掩盖路径碰撞。

### R2 / P1：下载没有跨进程单实例保护，登录终端也未纳入任务管理

位置：`tg_media_app.py:809`、`:820`、`:824`；`tg_media_archive.py:887`。
GUI 的 self.process 只保护自己启动的日志命令。终端 Popen 的返回对象被丢弃，
可以在登录/选群终端仍运行时启动下载；另开 GUI 或直接 CLI 也可共享同一个 root。
上传器有 SingleInstanceLock，下载器没有。多个会话所有者可能争用 session、SQLite、
同名 .part 和发布重命名。已复现终端进程未被追踪；未启动第二个真实下载器，
不声称已复现真实用户文件损坏。

建议：归档根目录级锁覆盖登录、索引、下载和选群；追踪终端子进程；GUI 多实例
聚合到既有窗口或只读查看。不要只检查进程名，也不要把 PyInstaller 父子包装误认成两个任务。

### R3 / P1：延迟清理只相信历史云验证，删除前未重新确认远端

位置：`cloud_uploader.py:916`、`:944`、`:953`；历史验证 `:876`。
remote_verified 持久保存并优先恢复清理。若验证后本地删除失败/关机，随后云对象被
删除或不可访问，下次启动仅核对本地 SHA-256 和配置安全门，仍会删除本地唯一副本。
临时 fixture 把远端校验配置为失败，purge 仍删除样本，且完全没有调用远端校验。
这验证的是“未复核远端”的逻辑，不是在用户网盘删文件。

建议：恢复后、延迟清理前重新 cryptcheck 并确认完整逻辑对象；验证失败保留本地。
保留“先 archived、再 unlink、再 local_purged”的恢复顺序，但不能只凭过期验证永久允许删除。

### R4 / P2：备份失败会直接退出上传器，下载仍可能继续

位置：`cloud_uploader.py:1015`、`:1020`，`ensure_daily_snapshot :764`。
磁盘不可用、镜像不可写或 SQLite 备份异常直接逃出 run_uploader；只有每文件操作
有异常重试。无上传守护恢复时，用户可能只看见下载窗口开着，而上传队列开始积压。
模拟镜像备份 OSError 已复现退出传播。

建议：备份独立告警和退避重试；默认不让备份故障终止上传主循环。上传进程本身
也要有可见的活性/失败状态和手动恢复入口，不能仅显示旧心跳时间。

### R5 / P2：运行中修改根目录会把安全停止写到错误目录

位置：`tg_media_app.py:582`、`:918`。
下载进程继续使用启动时参数，停止按钮却读取当前可编辑 root。用户从 A 改到 B
后停止，A 无停止标记，B 出现标记，30 秒后只能强制终止。临时双目录已复现。

建议：锁定运行中目录/账户设置，或保存每个任务不可变的 root 并用于停止、日志、
状态和守护，明确区分“当前查看目录”和“当前执行目录”。

### R6 / P2：真正退出窗口/托盘没有安全停止和等待

位置：`tg_media_app.py:962`、`:967`。
关闭到后台通常安全，但取消后台选项后关闭、或托盘退出，直接 destroy；不调用
停止流程、不等待子进程、不收尾输出读取。子进程与管道可能留存或随后报错退出，
不能把这个动作等同于文档里的安全停止。静态控制流确认，未在真实 GUI 上退出测试。

建议：退出变成受控状态机，先请求安全停止、后台等待、处理超时，再关闭托盘和
Tk；非交互终端也要统一管理。不要在 Tk 主线程阻塞等待。

### R7 / P2：恢复脚本跳过错误的同名已有文件并报告成功

位置：`cloud_archive/scripts/恢复文件.ps1:20`。
--ignore-existing 不检查已有内容。临时目录用真正的本机 rclone，来源为 correct、
目标为同样大小的 damaged，复制返回 0，目标依旧 damaged。恢复成功提示不代表
文件正确；当前没有 manifest SHA-256 的恢复后复核。

建议：默认恢复到空目录；非空目标先校验，冲突保留并明确报告，不自动覆盖用户文件。
支持以 manifest 校验恢复结果。复核上传和恢复两端的 local encoding 设置是否一致。

### R8 / P2：保存凭证脚本修改全局 HOME/.env

位置：`cloud_archive/scripts/保存百度开放平台凭证.ps1:27`、`:57`。
除工具 credentials 外，还重写用户主目录 .env 的 BAIDU_* 项，可能覆盖其他项目
的同名设置；不属于工具目录隔离模型。静态确认；本轮没有运行该脚本，也不展示任何凭证。

建议：默认只写工具专用 credentials；全局兼容选项必须显式选择并先做可恢复备份。
用户要求明文凭证是既定需求，本项不是对明文存储或用户授权提出异议。

### R9 / P2：增量索引协程仍无独立的网络无进展检测

位置：`tg_media_archive.py:604`、`:733`。
本轮 180 秒检测覆盖下载的连接/消息/分块，不覆盖 iter_messages 的每页等待。
当待下载列表为空、索引 RPC 长时间不返回时，下载主循环仍正常空轮询，不会触发
重建客户端，新消息可能一直无法入库。静态路径确认，尚未做真实 RPC 故障注入。

建议：为每页/消息等待加入可停止的无进展超时，并用统一客户端重连协调，不要让
索引自行创建第二个 session owner；正常群内没有新消息不能判为网络停滞。

### R10 / P3：可重复构建及操作日志边界仍不完整

位置：requirements*.txt、`cloud_uploader.py:524`、`:567`。
依赖主要使用版本区间，只有 OpenList/rclone 二进制版本锁定；无法精确复现 Python
依赖组合。rclone 临时日志在停止异常路径可能留存，成功后又先 read_bytes 整份
再截尾，大日志会产生不必要内存压力。静态确认，没有把它们当作本次退出的已证实原因。

建议：另存测试过的依赖锁与构建环境清单；临时输出在外层 finally 清理，使用 seek
读尾部，异常日志受限保留。开发和用户日志不能包含真实凭证。

## 证据与范围限制

运行 `.\.venv\Scripts\python.exe scripts\review_probes.py`：六个问题场景均复现。
这些 true 表示复现了缺陷，不是应用安全测试“通过”。脚本只操作 tempfile 下的
模拟目录/数据库/样本，其他进程完全 mock；恢复验证使用本地到本地 rclone，不访问网盘。

原修复回归测试 62 项全部通过；发布 EXE 为 x86_64，ZIP CRC 和运行数据排除检查通过。
原任务登录/断点保留，增量索引执行，现有 .part 持续增长，上传器心跳正常；未等待
当前大视频完整上传结束，也未检查全部历史视频的全流解码。

本轮没有模拟真实停电、真实云端文件消失、多账号登录、第二个真实下载进程或
其他电脑安装，没有鼠标键盘操作和 UI 视觉走查。系统级崩溃、上游平台内部行为、
第三方依赖安全漏洞不在这份源码审查的完整证明范围内。

## 推荐修复顺序

1. 先加根目录锁、固定任务上下文和群绑定，避免错误会话/文件写入。
2. 再补延迟清理前远端复验、恢复后校验和备份故障隔离。
3. 然后统一后台监督、索引停滞恢复、退出状态机和 GUI 状态展示。
4. 最后整理依赖锁、凭证作用域、日志与跨机器发布验收。

这几项适合独立提交、独立测试后分阶段部署，不应一次重写整个下载内核。
