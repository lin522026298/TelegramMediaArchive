# Telegram 加密云归档技术交接文档

最后更新：2026-08-07

本文面向维护者和接手项目的 AI。目标是从源码复现当前系统，并明确所有不能破坏的
数据一致性、重试、加密和部署约束。

## 1. 设计目标与边界

Telegram 下载内核继续由 `tg_media_archive.py` + Telethon 负责。云归档是独立侧车，
不把 Telegram 字节流直接管道到百度，也不替换已有下载和 `.part` 续传。

```text
Telegram API
  -> tg_media_archive.py
  -> 完整本地文件 + archive.sqlite3
  -> cloud_uploader.py
  -> rclone crypt
  -> rclone chunker
  -> OpenList WebDAV
  -> 百度网盘应用目录
```

关键取舍：单个文件必须先在本地完成。不可重放的 Telegram 流若直接接云端，任一层
断线都会失去可靠续传位置；以完整文件为缓存后，下载与上传各自拥有持久状态和校验。

## 3. Telegram 下载器必须保留的约束

- `media` 表按 `(chat_id, message_id, media_index)` 唯一。
- 调度按 `date_utc, message_id, media_index`。
- 并发只发生在有序批次内部。
- 每个文件写独立 `.part`，续传偏移来自磁盘实际长度。
- 完成后以原子 rename 变为正式文件，再标记 `downloaded`。
- `list_pending()` 必须排除 `downloaded` 和 `archived`，否则云端清理后会被重下。
- 每个新批次前检查 `state\cloud-backpressure.pause`。
- watch 模式在反压时等待；非 watch 模式干净退出。
- `--sync-new` 只能与 watch 模式一起使用；按当前 chat 的数据库最高 `message_id`
  作为 Telethon `min_id`，只增量索引后续图片/视频。
- 增量索引是下载进程中的独立 asyncio task，与下载协程共用一个 `TelegramClient`；
  禁止另开索引进程争抢同一 `.session`。
- `state\STOP_TELEGRAM_SYNC` 是安全停止哨兵。下载器在等待、批次边界和每个网络分块
  后检查，刷新 `.part` 与进度后退出；下一次 APP 管理的启动先删除旧哨兵。

`upsert_media()` 不得把已有 `downloaded` 或 `archived` 状态重置为 `pending`。

## 4. 上传队列与状态机

实现：`cloud_uploader.py`。队列来源仅为：

```sql
WHERE status='downloaded' AND local_path IS NOT NULL
```

本地路径先 `resolve()`，随后必须 `relative_to(<archive>\media)` 成功；`.part` 直接拒绝。
逻辑远端路径固定为 `archive/media/<原 media 相对路径>`。

状态机：

```text
discovered
  -> hashing
  -> uploading
  -> verifying
  -> remote_verified
  -> local_purged

任一上传阶段失败 -> error -> 指数退避 -> discovered 流程
清理失败         -> 保持 remote_verified -> 指数退避 -> 再清理
```

退避从 60 秒开始，最高 3600 秒。进程启动时只把 `hashing/uploading/verifying` 恢复为
`discovered`；`remote_verified` 绝不能退回上传阶段。

上传命令使用：

```text
rclone copyto <source> baidu_crypt:<remote>
  --local-encoding None
  --immutable --no-traverse
  --transfers 1 --checkers 1
  --bwlimit off --tpslimit 4
  --retries 10 --low-level-retries 20
```

`--bwlimit off` 表示不设置本机字节带宽上限。`--tpslimit 4` 仅约束 HTTP API 请求
突发频率，`--transfers 1` 仅保证单文件串行归档和清晰的删除边界；二者不把大文件
传输锁定到固定 MiB/s。OpenList 的低带宽上传模式只选择更小的百度分片以降低超时，
不是吞吐限速。动态上传 API 保持开启，用于选择可用的高速上传端点。

真实试验确认：同内容、同目标再次执行 `--immutable` 会安全跳过；不会覆盖或重复上传。
中断后 chunker 临时对象可由同一逻辑路径重试。

精确验证使用源文件父目录和 `--files-from-raw -`：

```text
rclone cryptcheck <source.parent> baidu_crypt:<remote.parent>
  --files-from-raw - --one-way --checkers 1
stdin: <remote basename>
```

该调用已分别对 1 MiB 和 270 MiB 样本实测通过。

Windows 本地后端必须显式使用 `--local-encoding None`。rclone 默认 local encoding
包含 `Question`，会把磁盘文件名中的全角问号 `U+FF1F` 解释为半角 `?`；Python
`stat()` 和 SHA-256 都成功，但 rclone 随后会报 `directory not found`。该问题已用
真实文件复现，并以禁用本地名称重解释修复。这个参数同时应用于 copy 和 cryptcheck。

## 5. 两阶段本地清理

上传验证与本地删除分成两个独立循环，不在同一个异常处理阶段内完成：

1. SHA-256 源文件。
2. 上传。
3. 确认上传期间大小和 mtime 未变。
4. `cryptcheck`。
5. 状态持久化为 `remote_verified`。
6. 下一轮重新读取 `remote_verified`。
7. 校验试点安全门和当前配置哈希。
8. 再次 SHA-256 本地文件。
9. 先将 Telegram DB 记录更新为 `archived`，要求恰好命中一行。
10. 只对该文件调用 `unlink()`。
11. 上传状态改为 `local_purged`。

先标记 DB、后删除文件是故意的：

- 若 DB 更新失败，文件仍在。
- 若 DB 成功但删除失败，下载器不会重下；上传队列保持 `remote_verified` 并重试。
- 若删除后、写上传状态前崩溃，重启时发现文件不存在，幂等重写 `archived` 后完成状态。

禁止递归删除。禁止用“上传命令退出码 0”直接作为删除依据。

## 6. rclone 加密与分块拓扑

实际 `config\rclone.conf` 有三层：

```ini
[openlist_webdav]
type = webdav
url = http://127.0.0.1:5244/dav/baidu-encrypted-archive/
vendor = other
bearer_token = <OpenList 永久令牌>

[baidu_chunks]
type = chunker
remote = openlist_webdav:/TelegramMediaArchiveEncrypted-v1
chunk_size = 256Mi
hash_type = md5all
meta_format = simplejson
transactions = rename

[baidu_crypt]
type = crypt
remote = baidu_chunks:
password = <rclone obscure 输出>
password2 = <rclone obscure 输出>
filename_encryption = standard
directory_name_encryption = true
```

调用方向是 `baidu_crypt -> baidu_chunks -> openlist_webdav`，数据处理方向为
`明文 -> crypt -> chunker -> WebDAV`。因此固定容器以下的目录名、文件名、chunk
元数据名称和内容都不泄露原名。

`rclone obscure` 只是可逆混淆，不是本机秘密保险箱。真正恢复依赖凭证文件中的明文
crypt password 与 salt。

## 7. OpenList 与百度配置

- OpenList v4.2.4 Windows amd64。
- 只监听 `127.0.0.1:5244`，不得监听 `0.0.0.0`。
- upload worker 和 transfer worker 均为 1。
- S3、FTP、SFTP、MCP 均关闭。
- 存储挂载：`/baidu-encrypted-archive`。
- 百度驱动根：`/apps/Encrypted Archive/加密上传用`。
- `use_online_api=false`，上传线程 1，timeout 600 秒。
- 动态上传 API、低带宽上传模式启用。

用户网盘根部原有 `/加密上传用` 能在 root list 中看到，但百度 API 无法进入，返回
`errno=-7`。因此正式存储位于应用目录 `/apps/Encrypted Archive/加密上传用`，不要
擅自改回根目录同名文件夹。

### OAuth 复现

直接自定义 callback 曾返回 `redirect_uri_mismatch`。最终使用 OpenList 官方 OOB 授权
页完成，授权码换得 access/refresh token。OpenList 保存令牌并负责刷新。

开发者凭证位于本机 `.env` 与 D 盘 `credentials`，不得输出到日志或 Git。

### Windows UTF-8 坑

Windows PowerShell 5.1 用普通字符串 POST JSON 时，中文挂载路径曾被静默写成问号。
调用 OpenList API 时必须：

1. `Content-Type: application/json; charset=utf-8`
2. 用 `[Text.Encoding]::UTF8.GetBytes($json)` 发送 body

否则 API 可能返回成功，但中文配置已经损坏。

### WebDAV 鉴权坑

OpenList Basic Auth 在 .NET PROPFIND 中可用，但 rclone 组合曾返回 401。当前配置使用
OpenList 永久 Bearer Token。`scripts\配置rclone加密链路.ps1` 从明文恢复文件读取
token，通过标准输入执行 `rclone obscure`，不把明文 crypt 密码放进命令行。

## 8. 删除安全门与试点

`manifests\pilot-verification.json` 必须同时为真：

- `restored_hashes_match`
- `cryptcheck_passed`
- `filename_encryption_verified`
- `multichunk_verified`

并且 `rclone_config_sha256` 必须等于当前配置 SHA-256。

试点源位于 D 盘，不触碰用户媒体：

- `small-sample.bin`：1 MiB
- `multichunk-sample.bin`：270 MiB，跨 256 MiB 边界

实测结果：2 个逻辑文件、5 个底层物理对象；cryptcheck 0 差异；回下载 SHA-256 一致；
物理名称中不含 `pilot`、`small-sample` 或 `multichunk-sample`。

更换 rclone/OpenList 版本、chunk size、crypt password/salt、远端或 WebDAV 配置后必须
重新试点并生成新门。不得手工篡改 JSON 绕过。

## 9. 顺序、锁与停止

- `next_ready()` 和 `next_verified()` 均按日期、消息 ID、媒体序号排序。
- 单实例锁使用 `msvcrt.locking()` 锁定持久 lock 文件第一个字节。
- PID 文件只用于操作入口；锁才是并发真相。
- 停止通过 `manifests\STOP_CLOUD_UPLOADER` 哨兵。
- rclone 活跃时每 5 秒检查哨兵，先 terminate，15 秒后才 kill 子进程。
- 启动脚本删除旧哨兵，先启动 OpenList，再隐藏启动上传器并等待新心跳。
- 不创建服务、启动项或计划任务。
- `scripts\启动连续归档.ps1` 依次启动 OpenList、上传器和 Telegram APP `--auto-sync`；
  已有 APP 窗口时改为隐藏启动 CLI，避免第二个 GUI。
- `scripts\停止连续归档.ps1` 必须先等待 Telegram CLI 安全退出，再停止上传器，最后
  停 OpenList。Telegram 超时不得强杀；上传器超时也不得绕过其安全停止。
- GUI 启动 CLI 时使用 Windows `CREATE_NO_WINDOW`，否则 console 子系统会弹出前台窗口。

## 10. 磁盘反压

常量：

```text
HIGH_WATER_BYTES = 100 GiB
LOW_WATER_BYTES  = 50 GiB
MIN_FREE_BYTES   = 150 GiB
```

`pending_bytes` 是所有尚未 `local_purged` 项的 `observed_size` 总和。若 free 小于最低线
或 pending 高于高水位，原子写反压 JSON。只有 free 恢复且 pending 低于低水位才删除
标记，形成迟滞，避免下载器频繁启停。

## 11. SQLite 快照

`sqlite_snapshot.py`：

1. `sqlite3.Connection.backup()` 写临时 DB。
2. `PRAGMA quick_check`。
3. `os.replace()` 原子发布。
4. 镜像先复制到临时文件，检查后原子发布。

Telegram GUI 每 5 分钟检查；上传器即使持续处理数天，也在每个状态循环中以 5 分钟
节流检查。因此只运行上传器时，`archive.sqlite3` 仍会得到每日一致性快照。


```powershell

```

只构建并部署侧车：

```powershell

  -Destination "D:\Cloud Storage\Openlist"
```

部署顺序：

1. 安全停止 Telegram 下载和旧上传器。
2. 保留 E 盘 `media`、`state`、`.session`。
3. 保留 D 盘 `data`、`credentials`、实际 `config`、`manifests`、`logs`。
4. 只替换 EXE、脚本、启动入口和文档。
5. 运行全部单元测试（0.1.4 基线为 48 项）。
6. 运行 `scripts\检查本地链路.ps1 -TestRemote`。
7. 确认试点门绑定当前配置。
8. 启动上传器并检查心跳、反压、首个真实文件状态。
9. 检查 Git diff 中无凭证后提交。

## 13. 测试最低矩阵

- 文件名清理、日期边界、分批顺序、`.part` 对齐。
- `archived` 不被 list_pending 重新选择。
- 反压路径固定在 archive state。
- 路径逃逸和 `.part` 被上传器拒绝。
- 安全门缺项或配置哈希变化会锁死删除。
- 本地 unlink 失败时，Telegram DB 已 archived，上传状态仍 remote_verified。
- 重启恢复不改变 remote_verified。
- SQLite backup 和镜像 quick_check。
- 真实 1 MiB 与跨 chunk 文件上传、cryptcheck、回下载 SHA-256。
- 已存在同目标的 immutable 重试。
- OpenList 仅环回监听。
- `--sync-new` 参数、数据库最高消息号 `min_id` 和同会话索引任务。
- Telegram 安全停止哨兵路径与 GUI `--auto-sync` 参数。

## 14. 凭证与 Git

绝不提交：

- `credentials\`
- 实际 `config\rclone.conf`
- OpenList `data\`
- `.env`
- OAuth token、AppKey/SecretKey/SignKey

## 15. 已知坑清单

- PowerShell 5.1 中文 JSON 必须显式 UTF-8 字节。
- `sqlite3.Connection` 上下文管理器只 commit/rollback，不保证 close；长期或测试代码用
  `contextlib.closing()`。
- PyInstaller onefile 首次启动需要解包时间，启动脚本应等心跳而非固定 sleep。
- `Start-Process -Wait` 可能等待 OpenList 拉起的进程树，启动 OpenList 应轮询端口。
- 不能依赖 PID 文件防双开，必须有 OS 文件锁。
- 上传后立即在同一异常阶段删除会制造崩溃窗口，必须保留两阶段状态。
- 先 unlink 再标 archived 会导致 DB 更新失败时被重新下载，顺序不可颠倒。
- Basic Auth 的成功探针不代表 rclone 同样可用，当前使用 Bearer Token。
- Windows local backend 默认会重解释全角保留字符；所有本地源命令必须带
  `--local-encoding None`。
- 百度网页不能预览密文是设计结果，不是上传损坏。
- 高并发对百度 API 可能降低稳定性，默认上传并发 1。
